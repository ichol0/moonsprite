# 性能基线

性能目标是保持像素编辑、画布移动和缩放的连续反馈。基准数据用于发现退化，不用于跨硬件比较绝对成绩。

每次更新的实际结果统一记录在 [性能更新记录](performance-history.md)。本文件只定义固定场景、测量方式和阈值。

## 当前自动基准

运行：

```powershell
pnpm bench:selection
```

2026-08-02 使用当前开发机重新检出修改前提交 `8c58f9b`，与当前提交交替运行，每个提交合并六次样本取中位数。该结果替代缺少环境快照的 2026-07-31 初始观察值，作为后续同机比较基线：

| 操作 | 平均耗时 | 观察阈值 |
| --- | ---: | ---: |
| 魔棒选择连续噪声背景 | 18.23 ms | 22 ms |
| 生成复杂选区边界 | 9.29 ms | 12 ms |

观察阈值不是跨机器硬失败线。同一机器连续三次中位数超过阈值，或比最近有效基线上升 5% 时需要解释，超过 25% 时阻止合并。

2026-07-31 记录的 `11.97 ms / 5.94 ms` 保留在性能历史中，但由于当前机器无法复现且当时没有保存运行环境、机器负载和完整原始样本，不再作为回归门禁。

### 画布交互

运行：

```powershell
pnpm bench:canvas
```

基准会先执行正式 Web 构建，再使用本机 Chrome 或 Edge、1280 × 800 视口和固定手势，分别测量 128 × 128、512 × 512、1024 × 1024 画布的平移、缩放、旋转后缩放和连续绘制。输出包括：

- `p50`、`p95`、`p99` 帧间隔和超过 25 ms 的比例。
- Canvas 主绘制的 `p95` 与最长耗时。
- 指针处理函数的 `p95` 与最长耗时。
- `PerformanceObserver` 捕获的最长主线程任务。

Headless Chromium 的 `requestAnimationFrame` 不锁定为 60 Hz，因此帧间隔只用于同机相对比较；主绘制和指针处理耗时可用于定位代码热点。正式体验仍需在 Windows WebView2 中手动复核。

2026-08-02 三次运行中位数：

| 画布 | 场景 | 帧 `p95` | >25 ms | 主绘制 `p95` | 指针处理 `p95` | 最坏帧 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 128 × 128 | 平移 | 3.70 ms | 0.307% | 0.30 ms | 0.20 ms | 117.9 ms |
| 128 × 128 | 连续绘制 | 3.70 ms | 0.286% | 0.90 ms | 0.40 ms | 99.9 ms |
| 512 × 512 | 平移 | 3.70 ms | 0.327% | 0.30 ms | 0.20 ms | 96.4 ms |
| 512 × 512 | 连续绘制 | 3.70 ms | 0.284% | 1.20 ms | 0.40 ms | 117.9 ms |
| 1024 × 1024 | 平移 | 3.70 ms | 0.316% | 0.30 ms | 0.20 ms | 103.6 ms |
| 1024 × 1024 | 缩放 | 3.70 ms | 0.640% | 0.40 ms | 0.20 ms | 35.7 ms |
| 1024 × 1024 | 旋转后缩放 | 3.70 ms | 0.213% | 0.50 ms | 0.20 ms | 29.0 ms |
| 1024 × 1024 | 连续绘制 | 3.70 ms | 0.285% | 1.10 ms | 0.40 ms | 121.4 ms |

主绘制和指针函数都明显低于 16.7 ms，但操作提交后仍存在约 96-121 ms 的异步长任务。当前证据指向订阅整个 Zustand store 后的 React 树更新，下一阶段应单独建立 React 提交分析并拆分 store 订阅，不能继续归因于 Canvas 绘制。

## 测量规则

- 使用固定输入数据和随机种子。
- 分开测量算法耗时、Canvas 重绘和完整指针事件延迟。
- 性能优化不得改变像素结果或交互契约。
- 每次修改基准输入、阈值或测量方式时记录原因和日期。
- 每次包含运行时代码的更新都必须追加性能历史；纯文档、注释或格式修改登记为“免测”。
