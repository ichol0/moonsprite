# AI 与开发自动工作流

中文 | [English](agent-workflow.en.md)

MoonSprite 以一个完整 `dev.X` 为开发单位。默认持续开发和 Debug，用户确认功能完成并明确要求发布时才集中执行发布门禁；不存在中间稳定批次。

## 零、文档读取语言

1. AI 日常只读取 `AGENTS.md`、`docs/README.md` 和不带 `.en.md` 后缀的中文契约。即使用户使用英文交流，也只切换回复语言，不切换或追加一套英文规则上下文。
2. 普通文档搜索必须排除 `*.en.md`，不得跟随文档顶部的 English 链接，也不得为了确认一致性而同时打开中英文版本。
3. 普通开发只修改中文文档。翻译、英文文档维护、双语一致性审计，以及发布阶段针对本周期变更文件的一次定向英文同步，是允许读取英文镜像的唯一例外。

## 一、开始需求

1. 检查 `git status`，区分已有未提交内容与本次将修改的文件；不得覆盖、回滚或把无关旧改动混入验证范围。
2. 阅读 `AGENTS.md`、`docs/README.md` 和任务直接相关的中文契约。D0/D1 不加载发布、性能、历史审计、ADR 或英文镜像；开发期间不读取历史更新日志，不为普通任务遍历 `docs/changelog/` 或 `docs/archive/`。
3. 将任务归入下表的风险等级。只在产品选择无法从最新用户要求、代码和契约推断时询问。

| 风险 | 典型范围 | 开发期最低检查 |
| --- | --- | --- |
| D0 | 文档、文案、CSS、纯视觉布局 | 无应用检查，用户验收 |
| D1 | 普通组件、菜单、弹窗、低频交互 | 类型检查和变更文件定向模块边界检查 |
| D2 | 一般 Store、共享状态、快捷键、Core/Shared Debug | 类型检查；仅在明确有价值时显式附带相关测试 |
| D3 | 坐标、选区、撤销、文件格式、持久化、平台安全、共享核心算法、复发或难发现 Bug | `--risk=high` 和定向回归测试；Rust 追加对应 `cargo check` |

文件数量不决定风险等级。人工可以根据真实影响上调；只有确认不涉及高风险语义时才能下调。

## 二、连续开发与 Debug

1. 定位根因并直接实现，不先创建发布文档、回归记录或性能记录。
2. 修改限制在相关模块。若修复必须跨模块，先说明依赖关系；架构债与非必要重构留到发布差异审计。
3. 每次完成修改后最多进行一轮最低检查，默认命令为：

```powershell
pnpm check:dev -- <本次实际修改文件...>
```

开发模式必须显式传入本任务文件；未传文件时直接失败，不扫描包含旧改动的整个工作树。D3 任务使用：

```powershell
pnpm check:dev -- --risk=high <源文件...> <相关测试文件...>
```

4. `check:dev` 的行为：

- 文档与维护文件不触发应用验证。
- 纯 CSS 不触发测试。
- TypeScript 代码触发类型检查。
- 普通 Core、Store、Shared Debug 不因目录位置自动要求测试；显式列出测试时只运行这些测试，不使用 `vitest related` 扩散范围。
- `--risk=high` 必须同时显式列出至少一个相关测试文件，否则检查直接失败。
- Renderer 变化只对本次显式传入的变更文件运行定向模块边界检查，不遍历整个 Renderer；完整边界扫描只在发布、架构审计或显式调用 `pnpm check:boundaries`（不带 `--files`）时运行。
- Rust 与缩略图变化只运行对应 `cargo check`，不构建安装包。

5. D3 Bug，以及曾复发、难以人工识别或共享算法中的 Bug，应补最小回归测试；其他 Bug 不要求先写失败测试，也不要求登记回归矩阵。
6. 修改通过最低检查后立即交给用户体验，并简短说明修改位置、可能影响范围和建议关注点。布局、视觉、动画手感与需求符合度以用户验收为准。
7. 除非用户明确要求，开发期间禁止自动执行：

- `pnpm check:release`、`pnpm check:maintenance`、全量测试或完整构建。
- 性能分级、性能基准和性能历史登记。
- 浏览器自动点击、截图对比、桌面端自动回归。
- 安装包、提交、推送、PR 和逐项 `CHANGELOG.md` 更新。

## 三、Debug 停止条件

- 有确定的编译、测试或运行时错误时，修复后可以重跑对应检查。
- 没有可复现证据时，不为“可能有问题”继续增加测试、自动验收或改动范围。
- 连续两轮修改仍未解决时，停止盲试并报告：已确认现象、当前根因判断、已排除项和下一步所需信息。
- 不因局部 UI 问题启动全项目重构。确有架构阻塞时先向用户说明成本与收益。

## 四、发布 dev.X

用户明确说“发布 dev.X”“准备发布”或“生成开发版”后：

1. 确认本周期基线提交 SHA，以该提交到当前工作树的完整 diff 作为本版本范围。
2. 集中审计重复实现、模块职责、数据格式迁移、临时兼容代码、调试代码、高风险回归和触及的性能关键区域。
3. 每个 `dev.X` 和正式版本先完成一次性能审计与有界优化：

```powershell
pnpm check:release-performance -- <本周期相关文件...>
```

审计器自动选择套件并生成一个稳定候选。具体 React 区域的重复计算、分配、订阅和刷新范围属于可自动尝试的低风险范围；像素、坐标、撤销、选区、格式、可变缓存和架构职责必须暂停并等待用户确认。每个候选最多两轮，修改后先运行相关正确性测试，再执行：

```powershell
pnpm check:performance:verify -- --audit=<审计编号> --correctness-passed
pnpm check:performance:accept -- --audit=<审计编号> --outcome=<adopted|not-adopted|approved-no-change> --reason=<原因>
```

没有超过噪声门槛的收益时恢复本次优化，并接受为 `not-adopted`；高风险候选经用户明确批准不改代码时使用 `approved-no-change --user-approved`。只有接受命令会更新机器基线、性能历史和发布凭证。

4. 根据实际 diff 集中更新：

- `CHANGELOG.md` 的“未发布”区，每个独立有效变化保留一条。
- 已发生行为变化的产品、交互或架构契约。
- 曾复发、难以人工发现以及 D3 Bug 的回归矩阵和测试。
- 架构计划的当前状态；不更新与本版本无关的文档。
- 中文文档定稿后，只对本周期实际修改且已经存在英文镜像的文件做一次定向同步；不读取或检查未变化的英文文档。

5. 运行发布正确性门禁：

```powershell
pnpm check:release
```

该命令先验证性能发布凭证与当前版本及源码指纹一致，再执行维护门禁、模块边界、全量前端类型与测试、Web 构建、Rust 检查和缩略图构建；它不重复运行性能基准，也不生成安装包。

6. 涉及真实桌面行为且需要自动门禁时运行 `pnpm check:release -- --desktop`。用户要求交付安装包时，再逐项执行 `docs/release/release-checklist.md`。
7. 发布完成后记录提交 SHA 作为下一个 `dev.X` 的基线。正式版本创建正式标签；开发版轻量标签只在用户需要时创建。

## 五、性能审计

普通需求不运行性能测试。每个 `dev.X` 和正式版本发布固定执行一次；日常只报告是否触及 Canvas、选区、像素算法、合成缓存、高频订阅、历史内存或大文件加载等关键区域。

除版本发布外，只有以下情况额外进入性能审计：

- 大版本或用户指定的阶段里程碑。
- 性能优化专项。
- 已观察到明显卡顿、长任务或内存异常。
- 用户明确要求性能检查。

进入审计后由 `pnpm check:performance -- <相关文件...>` 自动分级并选择定向场景；版本发布使用 `pnpm check:release-performance -- <相关文件...>` 强制最低 P3，固定运行 `128/512/1024` 标准画布、`800/2048/4000` 多内容大画布、`1024` 复杂动画工程和小范围 React profiling 哨兵。生产运行指标与 React profiling 指标使用独立生产构建和独立套件，禁止使用 Vite 开发服务器结果更新基线。单次矩阵扫描只用于候选发现和绝对预算告警，Canvas 历史退化必须由本次与已接受基线各至少三次样本支持。每个场景独立初始化，复杂撤销必须自行准备并验证历史深度；Canvas 候选使用三次样本中位数，算法 benchmark 使用自身统计误差。每次选择一个候选并最多优化两轮，只有最终接受时才更新基线、发布凭证和一条性能历史。GitHub 性能工作流仅手动触发并上传报告，不设置周期任务，也不写仓库。

## 六、安全与架构保护

- `core/` 不依赖 React、组件、平台和 Store；`store/` 不反向依赖组件；Tauri API 只从 `platform/` 访问。
- 组件只读取状态和收集输入，不直接修改文档或会话派生状态，不调用原始 `mutateActive`、`pushHistory`，也不直接开始、结束或写入 `HistoryStack`。文档写入和历史提交统一进入领域命令或 `begin/update/commit/cancel` 事务；预览必须覆盖确认、取消、切换文档和卸载清理。
- 撤销历史与工程格式解耦：`encodeProject`/`decodeProject` 不得作为历史快照，历史只保存受影响领域的最小差量。视图状态仍不得进入文档历史。
- 一次打开只执行一次完整解码；初始合成复用解码结果。标记为异步的保存、恢复和工程任务不得先在 UI 线程完整遍历、复制或压缩文档，再把结果交给 Worker。
- 恢复错误必须上报、记录或反馈给调用方，空 `catch` 和仅注释的 `catch` 均视为静默吞错。
- `core/` 生产运行时循环、在 `workspace.ts` 重建巨型根 `WorkspaceState`、渲染键像素序列化和按文件边界白名单均被禁止；新命令必须进入 `workspace-state.ts` 的明确领域契约。
- `check:dev` 使用静态导入检查只扫描本次变更文件，不以此改变历史债务预算；`pnpm check:boundaries` 不带 `--files` 时执行完整依赖方向扫描，不使用按文件放行历史例外。`pnpm check:architecture` 执行完整架构契约扫描；只有触及上述边界的开发任务才在最低检查中追加它，普通 UI 与 Debug 不额外运行。
- `scripts/architecture-debt-budget.json` 是现有迁移债务的唯一额度。额度必须等于扫描实数；债务减少时必须同步下调，禁止回升或推迟到期版本。`check:maintenance` 和发布门禁固定验证该契约。
- 坐标转换复用统一几何函数；视图状态不进入文档撤销历史。
- 文件格式变化必须包含兼容、迁移和失败回滚测试，必要时新增 ADR。
- 不强制推送，不覆盖用户改动，不提交生成目录、安装包、用户工程、恢复文件、工作区或密钥。

## 七、上下文恢复

对话压缩、换模型或隔一段时间继续时，读取本文件、`AGENTS.md`、当前分支、`git status` 和最近发布基线。恢复后仍默认处于 `dev.X` 开发中，不因上下文变化自动进入发布检查。
