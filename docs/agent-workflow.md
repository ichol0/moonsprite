# AI 与开发自动工作流

MoonSprite 以一个完整 `dev.X` 为开发单位。默认持续开发和 Debug，用户确认功能完成并明确要求发布时才集中执行发布门禁；不存在中间稳定批次。

## 一、开始需求

1. 检查 `git status`，区分已有未提交内容与本次将修改的文件；不得覆盖、回滚或把无关旧改动混入验证范围。
2. 阅读 `AGENTS.md`、`docs/README.md` 和任务直接相关的契约。开发期间不读取历史更新日志，不为普通任务遍历 `docs/changelog/` 或 `docs/archive/`。
3. 将任务归入下表的风险等级。只在产品选择无法从最新用户要求、代码和契约推断时询问。

| 风险 | 典型范围 | 开发期最低检查 |
| --- | --- | --- |
| D0 | 文档、文案、CSS、纯视觉布局 | 无应用检查，用户验收 |
| D1 | 普通组件、菜单、弹窗、低频交互 | 类型检查或相关测试 |
| D2 | Store、共享状态、快捷键、核心算法 | 类型检查和相关测试 |
| D3 | 坐标、选区、撤销、文件格式、持久化、Rust、平台 | 定向回归测试；Rust 追加对应 `cargo check` |

文件数量不决定风险等级。人工可以根据真实影响上调；只有确认不涉及高风险语义时才能下调。

## 二、连续开发与 Debug

1. 定位根因并直接实现，不先创建发布文档、回归记录或性能记录。
2. 修改限制在相关模块。若修复必须跨模块，先说明依赖关系；架构债与非必要重构留到发布差异审计。
3. 每次完成修改后最多进行一轮最低检查，默认命令为：

```powershell
pnpm check:dev -- <本次实际修改文件...>
```

4. `check:dev` 的行为：

- 文档与维护文件不触发应用验证。
- 纯 CSS 不触发测试。
- TypeScript 代码触发类型检查。
- Core、Store、Shared 改动必须在命令中附带相关测试文件；只运行显式列出的 Vitest，不使用 `vitest related` 扩散范围。
- Renderer 变化运行快速模块边界检查。
- Rust 与缩略图变化只运行对应 `cargo check`，不构建安装包。

5. D3 Bug，以及曾复发、难以人工识别或共享算法中的 Bug，应补最小回归测试；其他 Bug 不要求先写失败测试，也不要求登记回归矩阵。
6. 修改通过最低检查后立即交给用户体验，并简短说明修改位置、可能影响范围和建议关注点。布局、视觉、动画手感与需求符合度以用户验收为准。
7. 除非用户明确要求，开发期间禁止自动执行：

- `pnpm check:release`、`pnpm check:maintenance`、全量测试或完整构建。
- 性能分级、性能基准和性能历史登记。
- 浏览器自动点击、截图对比、桌面端自动回归。
- 安装包、提交、推送、PR 和逐项 `CHANGELOG.md` 更新。

## 三、Debug 停止条件

- 有确定的编译、测试或运行时错误时，修复后可以重跑对应检查。
- 没有可复现证据时，不为“可能有问题”继续增加测试、自动验收或改动范围。
- 连续两轮修改仍未解决时，停止盲试并报告：已确认现象、当前根因判断、已排除项和下一步所需信息。
- 不因局部 UI 问题启动全项目重构。确有架构阻塞时先向用户说明成本与收益。

## 四、发布 dev.X

用户明确说“发布 dev.X”“准备发布”或“生成开发版”后：

1. 确认本周期基线提交 SHA，以该提交到当前工作树的完整 diff 作为本版本范围。
2. 集中审计重复实现、模块职责、数据格式迁移、临时兼容代码、调试代码、高风险回归和触及的性能关键区域。
3. 根据实际 diff 集中更新：

- `CHANGELOG.md` 的“未发布”区，每个独立有效变化保留一条。
- 已发生行为变化的产品、交互或架构契约。
- 曾复发、难以人工发现以及 D3 Bug 的回归矩阵和测试。
- 架构计划的当前状态；不更新与本版本无关的文档。

4. 运行发布正确性门禁：

```powershell
pnpm check:release
```

该命令执行维护门禁、模块边界、全量前端类型与测试、Web 构建、Rust 检查和缩略图构建，但不自动运行性能基准或生成安装包。

5. 涉及真实桌面行为且需要自动门禁时运行 `pnpm check:release -- --desktop`。用户要求交付安装包时，再逐项执行 `docs/release/release-checklist.md`。
6. 发布完成后记录提交 SHA 作为下一个 `dev.X` 的基线。正式版本创建正式标签；开发版轻量标签只在用户需要时创建。

## 五、性能审计

普通需求和普通 `dev.X` 发布均不自动运行性能测试。日常只报告是否触及 Canvas、选区、像素算法、合成缓存、高频订阅、历史内存或大文件加载等关键区域。

只有以下情况进入性能审计：

- 大版本或用户指定的阶段里程碑。
- 性能优化专项。
- 已观察到明显卡顿、长任务或内存异常。
- 用户明确要求性能检查。

进入审计后先运行 `pnpm check:performance-scope -- <自上次基线以来的相关文件...>` 选择场景，再运行 `pnpm check:performance` 或更窄的定向基准。结果异常时才重复采样；有效结果与最近基线比较并记录到性能历史。GitHub 性能工作流仅手动触发，不设置周期任务。

## 六、安全与架构保护

- `core/` 不依赖 React、组件、平台和 Store；`store/` 不反向依赖组件；Tauri API 只从 `platform/` 访问。
- `pnpm check:boundaries` 使用静态导入检查阻止新的跨层依赖。脚本中登记的历史例外是待迁移债务，不得扩展白名单。
- 坐标转换复用统一几何函数；视图状态不进入文档撤销历史。
- 文件格式变化必须包含兼容、迁移和失败回滚测试，必要时新增 ADR。
- 不强制推送，不覆盖用户改动，不提交生成目录、安装包、用户工程、恢复文件、工作区或密钥。

## 七、上下文恢复

对话压缩、换模型或隔一段时间继续时，读取本文件、`AGENTS.md`、当前分支、`git status` 和最近发布基线。恢复后仍默认处于 `dev.X` 开发中，不因上下文变化自动进入发布检查。
